# AGENTS.md

## Scope

These instructions apply to the entire repository unless a more specific
`AGENTS.md` exists in a subdirectory.

## Project overview

`rn-native-search-bar` is an Expo module that exposes a native search bar for
React Native (iOS, tvOS and Android). TypeScript sources live in `src/`, native
code in `ios/` and `android/`. `example/` and `exampleTVOS/` are example apps,
`e2e/` contains end-to-end flows. `build/` is generated by `yarn build` and is
not committed.

## Verification

Run these before proposing a change (they mirror `.github/workflows/ci.yml`):

```sh
yarn lint
yarn typecheck
CI=1 yarn test
yarn build
```

## Commit conventions

Releases are derived from commit messages, so every commit on `main` and `beta`
must follow [Conventional Commits](https://www.conventionalcommits.org/):

- `feat:` creates a minor release (or the next beta prerelease on `beta`).
- `fix:` creates a patch release (or the next beta prerelease on `beta`).
- `feat!:` / `fix!:` or a `BREAKING CHANGE:` footer creates a major release.
  The legacy `breaking:` type from semantic-release is **not** recognized.
- `perf`, `refactor`, `revert`, `docs`, `chore` and `ci` appear in the
  changelog but do not trigger a release on their own.

## Release process

Releases are fully automated with
[Release Please](https://github.com/googleapis/release-please) via
`.github/workflows/release-please.yml`. There are two release channels, one per
branch, each with its own config, manifest and changelog so they never
interfere with each other:

| Branch | Channel    | Config                            | Manifest                             | Changelog           | npm dist-tag |
| ------ | ---------- | --------------------------------- | ------------------------------------ | ------------------- | ------------ |
| `main` | stable     | `release-please-config.json`      | `.release-please-manifest.json`      | `CHANGELOG.md`      | `latest`     |
| `beta` | prerelease | `release-please-config.beta.json` | `.release-please-manifest.beta.json` | `CHANGELOG-beta.md` | `beta`       |

Flow for both branches:

1. A push to `main` or `beta` opens or updates a release PR targeting that
   branch (`release-please--branches--<branch>--components--rn-native-search-bar`).
2. Merging the release PR bumps `package.json`, updates the branch's manifest
   and changelog, creates the `vX.Y.Z` tag and a GitHub release (marked as
   prerelease on `beta`).
3. The `publish` job then checks out the tag, builds the package and runs
   `npm publish` with the dist-tag of the branch. Authentication uses npm
   trusted publishing (OIDC) bound to `release-please.yml`, so there is no npm
   token secret. Renaming the workflow file breaks publishing until the trusted
   publisher on npmjs.com is updated.

Beta versions use the `prerelease` versioning strategy, so `1.0.0-beta.13`
becomes `1.0.0-beta.14` on the next release.

### Rules for agents

- Never bump `version` in `package.json`, edit the manifests or write changelog
  entries by hand; Release Please owns them.
- Never publish to npm or create tags manually; only the workflow publishes.
- Do not edit release PRs created by Release Please except when the user
  explicitly asks for it.
- Keep `main` and `beta` configs in sync. Only the prerelease settings
  (`versioning`, `prerelease`, `prerelease-type`, `changelog-path`) may differ.
- When merging between branches, `package.json` `version` conflicts are
  expected: keep the version of the target branch (`main` keeps its stable
  version, `beta` keeps its beta version). Manifests and changelogs are
  separate files and do not conflict.
- To promote beta to a stable release, merge `beta` into `main` and push a
  commit to `main` with a `Release-As: X.Y.Z` footer (for example
  `chore: release 1.0.0` with `Release-As: 1.0.0`).
- Changes to the release setup (workflow, configs, manifests) must be applied
  to both `main` and `beta`.
